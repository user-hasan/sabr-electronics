# صبر إلكترونكس — تعليمات العمل الأساسية

## الهدف
بناء تطبيق Flutter احترافي لإدارة محل **صبر إلكترونكس** لصيانة الأجهزة والإلكترونيات.

## قاعدة التشغيل
لا تبدأ بكتابة الكود مباشرة.

نفّذ دائمًا:

1. اقرأ جميع ملفات `docs/`.
2. افهم العلاقات بين المتطلبات.
3. افحص المشروع الحالي إن كان موجودًا.
4. تحقق من Flutter/Dart والحزم وواجهات Gemini الحالية قبل استخدامها.
5. أنشئ خطة تنفيذ.
6. اذكر التعارضات والمخاطر.
7. نفّذ Feature واحدة في كل مرة.
8. اختبر بعد كل Feature.
9. راجع التكامل مع بقية المشروع.
10. لا تعتبر المهمة مكتملة حتى تنجح الاختبارات والمراجعة.

## قواعد صارمة

- اسم التطبيق والهوية: **صبر إلكترونكس**.
- لا تستخدم "صابر إلكترونكس" في واجهة التطبيق أو الهوية.
- لا تخمّن API أو Package أو Model أو دالة غير مؤكدة.
- لا تستخدم API قديمًا لمجرد أنك تعرفه من مشروع سابق.
- لا تعدّل قاعدة البيانات مباشرة من Gemini.
- قاعدة البيانات هي مصدر الحقيقة الوحيد.
- Gemini مساعد للفهم والاستخراج والتحليل وتحديد النية، وليس مخزن البيانات.
- لا تحذف أو تستبدل بيانات المستخدم دون تأكيد مناسب.
- لا تنفذ عملية مالية أو تغيير حالة حساس اعتمادًا على تخمين AI.
- عند الغموض: توقف واذكر المشكلة بدل اختراع إجابة.
- حافظ على Offline-first للوظائف المحلية.
- لا تكسر وظائف موجودة أثناء إضافة وظيفة جديدة.
- لا تضع مفاتيح API داخل Git.
- لا تحفظ بيانات العملاء الكاملة داخل سجلات AI دون ضرورة.
- لا تعتبر الكود صحيحًا لمجرد أنه تم توليده؛ يجب التحقق والاختبار.

## أسلوب العمل

Analyze → Plan → Validate → Implement → Test → Review → Fix → Verify

## شرط التوقف

توقف واطلب التوضيح إذا:
- يوجد تعارض بين متطلبين.
- العملية قد تسبب فقدان بيانات.
- توجد هجرة Database مدمرة.
- API غير مؤكد.
- Package غير متوافقة.
- المتطلب المالي غير واضح.
- التعرف على الجهاز غير موثوق.
- لا يمكن ضمان سلامة العملية.
